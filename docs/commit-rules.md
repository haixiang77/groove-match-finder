# Git コミットルール（Conventional Commits ベース）

このエージェントがコミットする際の唯一の規約。司令塔はコミット前に本書を確認し、
worker-core / evaluator は差分の分割とメッセージ作成に必要な情報を本書に沿って扱う。
詳細な手順は `.claude/skills/self-healing-loop/SKILL.md` Step 7 を参照。

## 1. 基本フォーマット

シンプルな変更の場合は1行目（ヘッダー）のみで構いません。

```
<type>(<scope>): <subject>

<body>

<footer>
```

- `<type>`（必須）: 変更の種類を表す接頭辞
- `<scope>`（任意）: 変更の影響範囲（機能名、コンポーネント名、ディレクトリ名など）
- `<subject>`（必須）: 変更内容の要約
- `<body>`（任意）: 変更の背景・理由（1行目との間に必ず空行を1行入れる）
- `<footer>`（任意）: 関連 Issue 番号（`Closes #123`）や破壊的変更の通知

要件駆動のコミットでは、トレーサビリティのため footer に要件IDを残すことを推奨する。
例: `Refs: REQ-001`。scope は要件IDではなく、影響範囲（モジュール・機能名）を書く。
影響範囲が要件そのものに閉じる場合は、scope に要件IDを使ってもよい。

## 2. Type（接頭辞）一覧

- `feat`     : [新機能] ユーザー向けの新しい機能やエンドポイントの追加
- `fix`      : [バグ修正] 不具合・エラー・意図しない挙動の修正
- `refactor` : [リファクタリング] 仕様変更やバグ修正を含まない内部コードの改善・整理
- `perf`     : [パフォーマンス改善] 処理速度の向上、メモリ使用量の削減、クエリ最適化
- `style`    : [コードスタイル] 動作に影響しない修正（インデント、空白、フォーマット整形）
- `docs`     : [ドキュメント] README、仕様書、コード内コメントのみの追加・修正
- `test`     : [テスト] テストコードの追加、既存テストの修正
- `build`    : [ビルド・依存関係] パッケージ追加・更新（package.json等）、ビルド設定
- `ci`       : [CI/CD] GitHub Actions などのワークフローやデプロイ設定の変更
- `chore`    : [その他・雑務] .gitignore の更新、開発用スクリプト調整など上記以外の作業
- `revert`   : [取り消し] 過去のコミットの打ち消し（例: `revert: feat(auth): ログイン機能を追加`）

type は「何をしたか」ではなく変更の性質で選ぶ。要件完了でも、実態がバグ修正なら
`feat` ではなく `fix`、ドキュメントのみなら `docs` とする。

## 3. 記述の鉄則

### 1行目（Subject）のルール

- 簡潔にまとめる。英語なら50文字以内、日本語なら30〜40文字以内を目安にする
  （GitHub等のUIで省略されない長さ）。
- 末尾に句読点をつけない。英語のピリオド（.）や日本語の句点（。）は省く。
- 表現を統一する。
  - 日本語の場合: 「〜を追加」「〜を修正」「〜を削除」のように体言止め・簡潔な終止形で統一する。
  - 英語の場合: 命令形・現在形を使う（Added や Adds ではなく Add を使う）。

### 本文（Body）のルール

- 「What（何をしたか）」ではなく「Why（なぜ変えたか）」を書く。
  具体的なコードの差分は `git diff` を見れば分かるため、変更に至った背景・課題・
  設計判断の理由を残す。
- 1行目との間に必ず空行を1行入れる。Gitの各種ツールやパーサーがタイトルと本文を
  正しく分離するために必須。

### コミット粒度のルール

- 1コミット＝1関心事（Atomic Commit）。
  「バグ修正」と「無関係なファイルのフォーマット整形」を1つのコミットに混ぜない。
  後から `git revert` や `git bisect` で原因特定しやすくなります。
- 異なる目的の変更（機能追加とリファクタリング等）はコミットを分ける。

### 破壊的変更（Breaking Changes）の明示

- 後方互換性のない変更を行う場合は、`<type>` の直後に `!` を付与し、
  必要に応じてフッターに詳細を記載する。

```
feat(api)!: ユーザー取得APIのレスポンス形式を配列からオブジェクトに変更

BREAKING CHANGE: /api/users のルート要素が data プロパティ配下に変更されました
```

## 4. 良い例・悪い例

- × 悪い例: `修正`
  ○ 良い例: `fix(auth): トークン期限切れ時のリフレッシュ処理の無限ループを修正`
  → 何をどう直したか一目で分かるようにする
- × 悪い例: `機能追加とリファクタ`
  ○ 良い例: コミットを2つに分割する（`feat: ...` と `refactor: ...`）
  → 異なる目的の変更を1つにまとめない
- × 悪い例: `fix: ボタンを押したときの処理を直しました。`
  ○ 良い例: `fix(ui): 送信ボタンの二重クリック防止処理を追加`
  → 冗長な敬語・末尾の句点を省く

## 5. このエージェントでの運用

1. コミットは司令塔が Step 7（完了処理）で行う。worker-core はコミットしない。
2. コミット前に `git diff` / `git status` で差分を確認し、1コミット1関心事に
   分割できるか判断する。分割すべき場合は分割してからコミットする。
3. type は §2 から変更の性質で選び、scope は影響範囲を書く。
4. 複雑な変更・設計判断・破壊的変更がある場合は body に Why を必ず書く。
5. push はユーザー指示がある場合のみ行う（従来どおり）。
